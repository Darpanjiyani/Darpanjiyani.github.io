How I took text-to-SQL accuracy from 89.4% to 99.3%

Building an AI data agent that people outside tech can trust, one measured change at a time.

Darpan JiyaniNovember 20267 min readLive demo ↗Code ↗

Why I built itI wanted AI to do work, not just answer questions

Most of us use AI to look things up. I wanted to use it to automate the work I do every day as a data engineer. And I kept noticing the same thing at work: many people who need data aren't technical. To get one number, they have to ask someone and wait.

So I built an agent they can talk to in plain English. A router reads each request and sends it to one of two specialists: an SQL Analyst that answers questions from the database, and an ETL Analyst that pulls in new data and loads it, with a person's approval.

question → Claude router → SQL Analyst or ETL Analyst → SQL guard + LLM judge → PostgreSQL (read-only) → answer, chart and the exact SQL

The first version crashed before I could even score it. That's where the real work started.

Lesson 1Measure first

Before changing anything, I wrote 47 questions with verified answers: simple lookups, aggregations, joins, dates, and 13 hard ones. Each has a reference query. The agent only sees the question, and its result has to match the reference result.

89.4%My first honest score: 42 of 47. The agent looked smart in a demo. The test said otherwise.

The five failures were more interesting than the score. One crash came from a reply format I hadn't handled. A prompt rule to "always limit output to 10 rows" cut a 12-month breakdown to 10 months, and the answer then told the user the data ended in October. Another query divided by rated rides instead of all completed rides and reported 61.85% instead of 46.18%.

I fixed causes, not questions: a compact schema description with allowed values and sample rows, short notes about what the data means, and general SQL rules like "no filters nobody asked for" and "a percentage's denominator is the whole group." The SQL prompt even got 41% smaller. The next run scored 47 of 47.

Then I ran the same agent three times. Two runs scored 100% and one scored 97.9%: one query returned 56 rows that each said "1" instead of one row that said "56". A single run would have reported either 100% or 97.9%. The average of three, 99.3%, is the honest number. A later round added a check for results with the wrong shape, and it caught that query every time it slipped.

Because I'd written the fixes after seeing the failures, I needed proof they generalized. So I kept 20 held-out questions I never tuned on, and later wrote a second set of 20 after the last change. Both scored 100%.

Lesson 2Don't rely on the prompt for safety

A prompt that says "never change data" is a request, not a guarantee. My agent has three layers. It connects as a read-only database user. A rule-based guard (sqlglot) allows exactly one read-only SELECT. An LLM judge reviews what's left. Data loads need a person's approval.

0 of 22requests to change data ever ran. Every one was refused with a clear message, including vague follow-ups like "delete them."

Measuring safety taught me something too. After one prompt change, nothing unsafe ran, but some refusals got confusing: asked to update users, the agent quietly wrote a read query instead. "Nothing executed" was the wrong test. I added "clearly refused" as its own metric and fixed it.

Lesson 3Your tests can be wrong too

The scorer for my ETL agent compared each column on its own. So a table with every value right but on the wrong rows passed, like Montreal's weather filed under Ottawa's name. I tested the scorer itself with 100 deliberately wrong outputs.

25 of 100wrong outputs slipped past the old scorer. The new one compares whole rows and rejects all 100.

Even my very first run had this problem the other way around: four "failures" were the scorer being too strict, not the agent being wrong. Now I check the checker before I trust a number.

Lesson 4Let it say "I can't answer that"

I asked 15 questions the data couldn't answer, like tips or a driver's age. Only 2 replies handled it well. Some errored out. Worse, two answered a different question as if it were the one asked: the total of all fares was reported as the company's commission.

The surprise: in 8 of 15 cases the model already knew the data was missing. My own SQL guard turned its honest sentence into an error. I gave it a clear way to say what's missing, and checked 12 look-alike questions so it wouldn't start refusing good ones.

2 → 14of 15 replies now say exactly what's missing, with 0 wrong-question answers, and all 12 look-alike questions still answered correctly.

The hardest partTwo agents that depend on each other

Getting everything to work together was the hardest part. The ETL Analyst has to load data cleanly before the SQL Analyst can answer anything about it. A small mistake in the load quietly becomes a wrong answer later. Questions that mixed newly loaded weather data with rides went from 0 of 12 to 11 of 12 once the two halves really worked together.

The surprise20.8 million real trips

I pointed the agent at one month of real New York City Uber and Lyft trips: 20.8 million rows, a thousand times more than the data I built it on. I expected it to fall apart. It answered 27 of 28 new questions exactly, at the same cost per question, because the model only reads the schema and small results, never the table.

The model held up. The work was in the plumbing around it. Describing the schema took 42.7 seconds on that many rows, and now takes 0.1. And when one slow query hit the time limit, the retry quietly computed a median from a random 5% sample. Now the agent stays exact, and every heavy question in a new test set passes: 12 of 12, up from 8.

Start small. Write the questions first. Then build.

If I could tell one thing to anyone building an AI tool: decide how you'll know it works before you make it work. The tests on this page were written before the fixes they measure.
